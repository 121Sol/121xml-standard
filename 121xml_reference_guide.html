🎯 Overview

121XML is a vendor-neutral, self-describing data format designed to solve critical problems in AI systems:

📉 30-50% Information Loss

Per compaction cycle in context windows. 121XML eliminates this through content addressing.

💾 78% Token Waste

Over conversations. 121XML achieves 90-96% compression with zero data loss.

🔒 Vendor Lock-in

Across Claude, GPT, Gemini, Llama. 121XML enables perfect portability.

👑 Data Sovereignty

Centralized control. 121XML: "Data lives where the user decides."

🏛️ Three Core Axioms

Foundation principles that define 121XML's architecture:

AXIOM 1

Composition Over Inheritance

Principle: Objects are built by composition, not hierarchical inheritance.

Benefit: Flat, predictable structure. No deep class hierarchies.

{
  "_type": "payment",
  "amount": 450000,
  "currency": "USD",
  "sender": { "_type": "party", "name": "Acme Corp" },
  "receiver": { "_type": "party", "name": "Smith Ltd" }
}
AXIOM 2

Explicit Type Tags

Principle: Every object carries its type explicitly via _type field.

Benefit: Self-describing, schema-discoverable, no type ambiguity.

{
  "_type": "mcp_resource",
  "_schema": "urn:121xml:mcp-resource/1.0",
  "uri": "banking://schema/swift",
  "content": "..."
}
AXIOM 3

Homogeneous Sequences

Principle: Arrays contain objects of the same type only.

Benefit: Predictable iteration, efficient compression, type safety.

{
  "_type": "payment_list",
  "payments": [
    { "_type": "payment", "id": "pay_001", ... },
    { "_type": "payment", "id": "pay_002", ... },
    { "_type": "payment", "id": "pay_003", ... }
  ]
}

⚙️ Four Core Rules

Operational rules that ensure consistency and efficiency:

RULE 4

Alphabetically Sorted Keys (R4)

Specification: All object keys must be sorted alphabetically at every level.

Purpose: Enables deterministic hashing and comparison.

CORRECT ✓
{
  "_address": "data://sha256:abc123:payment",
  "_schema": "urn:121xml:payment/1.0",
  "_type": "payment",
  "amount": 450000,
  "currency": "USD"
}

WRONG ✗
{
  "amount": 450000,
  "_type": "payment",
  "currency": "USD",
  "_address": "data://sha256:abc123:payment"
}
RULE 5

Explicit Null vs Absent (R5)

Specification: Distinguish between null (explicitly empty) and absent fields.

Purpose: Precise data intent, enables lossless reconstruction.

// Field explicitly null (value: unknown/empty)
{
  "sender": null,  // Known to be null
  "receiver": { ... }
}

// Field absent (not present)
{
  "receiver": { ... }
  // sender key not present = different meaning
}
RULE 6

Profile URI for Schema Discovery (R6)

Specification: Every object includes _schema field with URN pointing to schema.

Purpose: Enables automatic schema discovery and validation.

{
  "_type": "payment",
  "_schema": "urn:121xml:payment/1.0",
  "_address": "data://sha256:abc123:payment",
  "amount": 450000
}

// Schema URN structure:
// urn:121xml:{object-type}/{major-version}.{minor-version}
RULE 7

SHA256 Content Addressing (R7)

Specification: Content address format: data://sha256:HASH:TYPE

Purpose: Immutable, deterministic addressing enables perfect deduplication.

// Computation:
// 1. Sort keys alphabetically
// 2. Serialize to JSON (compact, no spaces)
// 3. Compute SHA256 hash
// 4. Take first 16 characters of hex hash
// 5. Format: data://sha256:{hash}:{type}

// Example:
data://sha256:f84b8556e9174280:payment

// Properties:
// - Same data = Same address (idempotent)
// - Different data = Different address (collision-free)
// - Enables deduplication and archival

💡 Key Concepts

Content Addressing

Concept: Every data object gets a unique, immutable address based on its content.

Format: data://sha256:HASH:TYPE

Properties:

  • ✓ Deterministic - same data = same address
  • ✓ Immutable - changing data changes address
  • ✓ Collision-free - different data = different address
  • ✓ Enables deduplication - identical objects referenced once

Lossless Compression

Concept: Reduce token usage 90-96% with zero data loss.

Method: Replace full objects with sparse content references.

BEFORE (2,500 tokens):
{
  "messages": [
    { "id": "msg1", "content": "hello world...", ... },
    { "id": "msg2", "content": "how are you...", ... },
    { "id": "msg3", "content": "i am fine...", ... }
  ]
}

AFTER (250 tokens):
{
  "messages": [
    { "id": "msg1", "_address": "data://sha256:abc123:message" },
    { "id": "msg2", "_address": "data://sha256:def456:message" },
    { "id": "msg3", "_address": "data://sha256:ghi789:message" }
  ],
  "_archived": ["data://sha256:abc123:message", ...]
}

Data Sovereignty

Concept: User controls where and how their data is stored.

Three Layers:

  1. User Decision: User chooses storage location
  2. Permission Grants: User grants access permissions per object
  3. Encrypted Storage: Data encrypted with user's keys

Vendor-Neutral Portability

Concept: 121XML works identically across Claude, GPT, Gemini, Llama.

Benefit: No vendor lock-in, switch AI systems without data loss.

🔗 Content Addressing System

Address Format

data://sha256:{HASH}:{TYPE}

Example Addresses

data://sha256:f84b8556e9174280:payment
data://sha256:3ff3c20c05ff0106:message
data://sha256:1418c9f2b7d5e8a1:resource
data://sha256:0367ab79c1383078:party
data://sha256:a7b96ce3e2a3f5c0:tool

Address Computation Algorithm

1. Sort all keys alphabetically
2. Remove any _address field
3. Serialize to JSON (compact, no spaces):
   json_str = json.dumps(obj, sort_keys=True, separators=(',', ':'))
4. Compute SHA256 hash of bytes:
   hash = sha256(json_str.encode()).hexdigest()
5. Extract first 16 characters:
   short_hash = hash[:16]
6. Format address:
   address = f"data://sha256:{short_hash}:{type}"

Properties of Content Addressing

✓ Deterministic

Same object always produces same address. Enables perfect deduplication.

✓ Immutable

Changing even one byte changes the address. Detects tampering.

✓ Collision-Free

Different objects produce different addresses (256-bit security).

✓ Self-Describing

Address includes object type, enabling automatic schema discovery.

Conversion Algorithm

// MCP request to 121XML conversion
function translate_mcp_to_121xml(mcp_request) {
  1. Extract method and params
  2. Determine object type from method
  3. Create 121XML object with:
     - _type: determined from method
     - _schema: URN for schema discovery
     - _address: computed from content hash
     - All params included
  4. Return 121XML object
}

// 121XML back to MCP conversion (lossless)
function translate_121xml_to_mcp(xml_121_obj) {
  1. Extract original method from metadata
  2. Extract params (remove _ prefixed fields)
  3. Create MCP JSON-RPC request
  4. Return unchanged (perfect restoration)
}

🔌 Plugin System

Plugin Architecture

121XML uses auto-generated plugins from schemas:

Plugin Structure

121xml-banking/
├── plugin.json          # Plugin manifest
├── SKILL.md            # Skill definition
├── schema.121xml       # Embedded schema
└── README.md           # Documentation

// plugin.json structure
{
  "name": "121xml-banking",
  "version": "1.0.0",
  "description": "Banking workflows plugin",
  "capabilities": ["tools", "resources", "prompts"],
  "tools": [
    {
      "name": "swift_wire_transfer",
      "description": "Execute SWIFT wire transfer",
      "input_schema": { ... }
    }
  ]
}
